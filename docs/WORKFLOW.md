# 멀티 에이전트 브랜치·릴리즈 프로토콜

여러 에이전트(사람 포함)가 같은 저장소에서 동시에 작업할 때의 규칙이다. 신규 기능과 수정은 **항상 새 브랜치**에서 하고, 릴리즈 때 **릴리즈 통합 브랜치**에서 합친다. `scripts/RELEASING.md`(릴리즈 체크리스트)와 함께 적용한다.

## 1. 원칙

1. `main`에 직접 커밋하지 않는다. 기능·수정은 전부 작업 브랜치에서 한다.
2. 작업 하나 = 브랜치 하나 = 에이전트 하나. 같은 브랜치를 두 에이전트가 동시에 만지지 않는다.
3. 작업 브랜치에서는 `VERSION`, `docs/releases/*`, `docs/DEVELOPMENT.md`를 수정하지 않는다. 충돌의 주된 원인이라 릴리즈 담당만 건드린다.
4. 이미 게시된 버전(`v*` 릴리즈)의 파일은 절대 덮어쓰지 않는다. 수정은 더 높은 버전으로 낸다.
5. 내가 만들지 않은 미커밋 변경을 발견하면 스테이징·되돌리기·덮어쓰기를 하지 않는다. 다른 에이전트의 작업이다.

## 2. 브랜치 이름

| 종류 | 이름 | 시작점 |
|---|---|---|
| 기능 | `feat/<짧은-주제>` | `origin/main` |
| 수정 | `fix/<짧은-주제>` | `origin/main` |
| 핫픽스(게시된 버전 기준) | `fix/<주제>` | 해당 태그 (예: `v0.4.11`) |
| 릴리즈 통합 | `release/<버전>` | 아래 5절 |

주제는 영문 소문자와 하이픈만 쓴다. 예: `feat/mrpack-export`, `fix/mod-unknown-warning`.

## 3. 작업 시작과 진행

작업 폴더를 공유하면 다른 에이전트의 미커밋 변경과 섞인다. **작업마다 별도 워크트리**를 쓴다.

```bash
git fetch origin
git ls-remote --heads origin 'feat/<주제>' 'fix/<주제>'   # 같은 이름이 있으면 다른 에이전트가 이미 점유 중 -> 이름을 바꾸거나 협의
git worktree add ../luonotar-<주제> -b feat/<주제> origin/main
cd ../luonotar-<주제>
git push -u origin feat/<주제>                            # 빈 브랜치라도 먼저 푸시해 점유를 알린다
```

- 작은 단위로 자주 커밋하고, 하루 한 번 이상 `git fetch && git rebase origin/main`으로 최신 `main`을 따라간다.
- 커밋 메시지는 무엇을 왜 바꿨는지 쓴다. 에이전트 공동 작성 표기가 있으면 마지막 줄에 넣는다.
- 테스트는 변경한 범위의 것만 돌린다. 전체 테스트는 릴리즈 통합 단계에서 한 번 돌린다(사용자 요청: 3개 빌드마다 통합 테스트).
- 끝나면 푸시하고 **인계 메모**를 남긴다(아래 4절 참고).
- `docs/DEVELOPMENT.md`에 쓸 내용은 인계 메모에 적어 두고, 릴리즈 담당이 릴리즈 때 한 번에 옮긴다.

## 4. 진행 상황 공유 (공유 파일 없음)

진행 상황은 **`main`에 두는 공유 파일이 아니라** 각 에이전트가 자기 브랜치에만 쓰고, 읽을 때 git에서 모아 본다. 쓰는 곳이 서로 달라 충돌이 생기지 않고, `main`은 릴리즈 때만 바뀐다.

| 정보 | 위치 |
|---|---|
| 누가 무엇을 하는가(점유) | 푸시된 브랜치 이름 |
| 지금 어디까지 했나 | 자기 브랜치의 `docs/dev-notes/<브랜치 이름의 /를 -로 바꾼 것>.md` |
| 한눈에 보는 현황 | `scripts/agent-status.sh` (읽기 전용, 아무것도 커밋하지 않음) |
| 협의가 필요한 질문 | 해당 브랜치의 드래프트 PR 코멘트 (`gh pr comment`) |

노트 파일 규칙 (예: 브랜치 `feat/mrpack-export` → `docs/dev-notes/feat-mrpack-export.md`):

```markdown
상태: 팩 내보내기 API 구현 중, UI는 아직
# feat/mrpack-export
- 변경 요약 / 영향 파일
- 실행한 테스트와 결과, 실행하지 못한 테스트와 이유
- 다른 작업과 맞물리는 점 (예: Mods.tsx를 같이 수정하는 브랜치가 있음)
- 릴리즈 노트에 넣을 한국어 한두 줄
```

- 첫 줄 `상태: …` 한 줄은 현황판이 그대로 보여준다. 단계가 바뀔 때마다 고쳐 쓰고 푸시한다.
- 시작 전과 파일 구조를 크게 바꾸기 전에 `scripts/agent-status.sh`를 실행해 같은 파일을 만지는 브랜치가 있는지 확인한다. "겹치는 수정 파일"에 걸리면 상대 브랜치의 노트를 읽고(`git show origin/<브랜치>:docs/dev-notes/<파일>.md`), 필요하면 PR 코멘트로 순서를 맞춘다.
- 병합이 끝난 브랜치의 노트는 릴리즈 담당이 `docs/DEVELOPMENT.md`로 옮긴 뒤 브랜치와 함께 정리된다.

## 5. 릴리즈 통합 절차

릴리즈 담당 한 명이 수행한다. 어떤 브랜치를 넣을지는 사용자가 정한다. 검증이 끝나지 않은 브랜치는 넣지 않는다.

1. **범위 확정**: 포함할 작업 브랜치 목록과 버전을 정한다. 버전은 `major.minor.patch` 또는 `-beta.N`. 이미 게시된 버전보다 높아야 한다.
2. **통합 브랜치 생성**
   ```bash
   git fetch origin --tags
   git worktree add ../luonotar-release-<버전> -b release/<버전> origin/main      # 일반 릴리즈
   # 핫픽스: ... -b release/<버전> v<게시된 버전>  (이후 필요한 수정 커밋만 cherry-pick)
   ```
   시작 전에 `scripts/agent-status.sh`로 병합 대상 브랜치의 상태, 뒤처짐, 겹치는 파일을 확인한다.
3. **병합**: 의존이 적은 브랜치부터 `git merge --no-ff origin/<브랜치>`로 하나씩 합친다. 충돌은 이 단계에서만 해결하고, 해결 내용을 커밋 메시지에 남긴다. 한 브랜치를 합칠 때마다 컴파일(`./gradlew compileKotlin`)과 프런트 빌드가 되는지 확인한다.
4. **릴리즈 파일**: `VERSION` 갱신, `docs/releases/<버전>.md`(한국어), 필요하면 `docs/DEVELOPMENT.md`에 인계 메모를 옮긴다.
5. **전체 검증**: `npm ci --prefix frontend && npm run build --prefix frontend`, `./gradlew test bootJar`, 관련 Playwright 테스트. 실패하면 원인 브랜치로 돌려보내거나 통합 브랜치에서 고친다. 실행하지 못한 테스트는 "미실행"으로 기록하고 통과했다고 쓰지 않는다.
6. **게시**: `release/<버전>`을 푸시한 뒤 태그 `v<버전>`을 같은 커밋에 만들어 푸시한다. 태그가 `VERSION`과 일치해야 `release.yml`이 통과한다. CI가 테스트, 패키징, 서명, 게시를 수행한다.
   - 게시 전에 실패하면 태그를 고친 커밋으로 옮겨 다시 푸시해도 된다(릴리즈가 만들어지기 전에 한해서).
   - 게시된 뒤에는 태그와 파일을 건드리지 않는다.
7. **마무리**: 게시가 성공하면 `release/<버전>`을 `main`에 `--no-ff`로 병합하고 푸시한다. 병합된 작업 브랜치는 삭제하고 워크트리를 `git worktree remove`로 정리한다. 포함되지 않은 작업 브랜치는 새 `main` 위로 rebase한다.
8. **보고**: 사용자에게 포함된 브랜치, 실행한 테스트와 못 한 테스트, 릴리즈 주소를 알린다.

## 6. 충돌을 줄이는 규칙

- 같은 파일을 여러 브랜치가 크게 바꿔야 하면 먼저 사용자에게 순서를 묻는다.
- 포매팅만 바꾸는 대규모 변경과 파일 이동은 별도 브랜치로 먼저 `main`에 넣는다.
- 생성물(`src/main/resources/static/`, `build/`, `test-results/`)은 커밋하지 않는다.
- 비밀 값(`.release-keys/`, 토큰, 프로필 데이터)은 어떤 브랜치에도 커밋하지 않는다.

## 7. 요약 (에이전트용 체크리스트)

- 시작: `fetch` → `scripts/agent-status.sh`로 점유·겹침 확인 → 워크트리로 새 브랜치 → 즉시 푸시
- 진행: 작은 커밋, 주기적 rebase, 범위 테스트, `VERSION`·릴리즈 문서 금지, 노트의 `상태:` 줄 갱신
- 종료: 푸시 + 인계 메모
- 릴리즈: `release/<버전>`에서 병합 → 전체 검증 → 태그 푸시 → `main`에 병합 → 정리
