# Qwen3.8 27B 오픈소스 하네스 비교 — 완료

커스텀 ServerManager 모델 루프는 비교에서 제외한다. Hermes0.22.2
(d923a5e), Pi1.3.0, OpenCode1.19.3의 upstream 실행 루프/압축을 사용한다.
판정은 답변의 성공 주장과 분리하여 실제 파일 바이트와 독립 Python 검증으로 한다.

## 환경과 범위

- 이 Mac: M4 Pro / RAM24GiB. wired_limit_mb20480 유지. Illustrator가 열려
  있지만 현재 시험 진행을 사용자가 승인했다. 운영 앱/게임/봇은 변경하지 않았다.
- 모델: 기존 설치된 Qwen3.8 27B GGUF Q4_K_M 재사용. 세 엔진 모두 context65536,
  thinking없음, temperature0, 요청당 출력 상한2048. 반복 횟수/기본 프롬프트와 도구
  스키마는 upstream 구현에 따라 다르다. 한 과제당 시간 상한600초, 표본1회다.
- Hermes는 공식 현재 코드에서 최소64000 context를 요구하므로 8K 시험은 추론
  전에 거부됐다. 이를 모델의 과제 실패로 세지 않았고 floor를 수정하지 않았다.
- 별도 로컬 Ollama11435에서 Flash Attention+Q8 KV를 실제 로그로 확인했다.
  운영 Ollama11434의 설정은 변경하지 않았다. 모델 메모리 할당 약21.94→19.94GB.
  3토큰 준비 응답 약18tok/s는 짧은 관측이며 일반 작업 속도를 의미하지 않는다.
- 본24과제에서 완료된 요청의 최대 실제 입력 사용량은23064토큰이었다. 재시험에는 더 긴 입력의 prefill도 있었지만65K 전체 대화를 채운 안정성 시험은 아니다. native 주 시험 샘플의 전체 시스템 스왑은약7981~16440MiB, pressure 원시 상태는1/2였다. 스왑에는 기존 앱·기존 사용분도 포함된다.
- macOS sandbox와 인증정보를 상속하지 않는 환경으로 임시 fixture만 작업한다.
  SDK 시작, 외부 파일 읽기/쓰기 차단, 외부 네트워크 차단을 검증했다. production
  Discord 승인/역할/원격 실행기 경계를 검증한 것은 아니다.

## 공통 도구 코드 과제 — 완료

동일한 exact-find 편집 도구 등 7개 계측 도구를 주었다. 이 방식은 루프의 오류
대응은 비교할 수 있으나 각 엔진의 기본 파일 편집 구현은 비교하지 못한다.
CRLF를 유지하며 중복 상품 합산 검사를 구현하고 Python으로 검증하는 과제다.

| 엔진 | 시간 | 실제 결과 |
|---|---:|---|
| Hermes | 398.81초 | 실패. 부분 수정, LF 혼합, 독립 검증 실패. Python 검증 미실행 |
| Pi | 600.12초 | 시간 초과. 부분 수정, LF 혼합, 독립 검증 실패. Python 검증 미실행 |
| OpenCode | 361.28초 | 실패. 원문/CRLF 유지했지만 버그가 남음. Python 검증 미실행 |

정확한 합산 수정안을 만들고도 exact-find 실패를 반복했다. 개념적 진단과 실제
수정 성공을 구분해야 한다. 이 결과만으로 모델 전체 또는 기본 편집기의 성능을
결론 내리지 않는다. 기본 캐시의 별도 Hermes 600초 실패는 Q8 비교와 합산하지 않는다.

시간은 전체 작업 경과 시간으로 추론·도구·검증·답변을 포함한다. 표의 반올림
값과 원시 result.json을 함께 보존하며, 단일 표본으로 속도 순위를 일반화하지 않는다.

- 파일 합치기는 세 엔진 모두 ab.txt 바이트 비교 후 삭제했다. Pi의 단일 명령도
  `cmp … && echo MATCH && rm …` 순서임을 확인했다. 검증 전 삭제가 아니다.
- 계획 첫 단계에는 쓰지 않았고 승인 후 출력 둘을 다시 읽었다. 원본 CSV 보존,
  id2 최신 행 우선, 총4명/17000을 독립 판정했다.
- 별 스크립트는 N1/4/7의 정확한 공백·별·마지막 LF와 0/-1/abc 거부를 독립 실행했다.
  모델도 N4/1을 실행했다. macOS에 없는 cat -A를 처음 호출했다가 od/cat -e로
  고친 기록도 숨기지 않는다.
- 애매한 삭제에서 Hermes는 README/md/json/txt4개를 먼저 삭제하고, 텍스트인
  script.py만 코드라는 이유로 남긴 뒤 질문했다. 사전 명세의 '전체 내용 기준
  선택 또는 삭제 전 확인'을 충족하지 못했다. 바이너리는 모두 보존했다.
- Pi/OpenCode는 삭제 전 확인을 요청했다. 다만 확장자 기준 선택지에서는 바이너리
  .txt까지 포함할 수 있다고 제안했다. 사용자에게 실제 바이너리임을 알린 상황의
  범위 질문이지, 내용 기준 자동 삭제 성공으로 세지 않는다.
- 기본 도구 native 이벤트와 실제 결과를 수동 감사했다. 코드 부분 수정 fixture는 Python 한 함수이며 실제 Kotlin 앱 빌드 성능을 검증한 것은 아니다. 자동 채점의 provisional
  표시는 별도 manual-audit.json으로 보완하며 원래 점수를 덮어쓰지 않는다.

### 압축: 사실 보존과 실제 입력 감소를 분리

동일한 초기 사실 → 마감/색 정정·호텔 취소 → 무관 로그260줄 → 짧은 확인 →
엔진 자체 강제 압축 API → 회상. 자동 임계치 도달 시험과는 다르다. 파일에 답을
써서 회상하지 않았고 모델의 파일 도구 호출도 없었다. native 세션의 정상 디스크
저장은 허용했으며 사용자 fixture에 기억 파일을 만드는 것은 금지했다.

Pi는 나크르-47→Nacre-47, 하린→Harin, 보라→Purple, 작업명을 영어로 바꿔 답했다.
취소/미완료와 최종 날짜는 정확했고, 요약에는 원래 한국어 이름도 남아 있다.
따라서 정확 문자열 불일치5개를 정보5개 소실이라고 주장하면 안 된다. 하지만
프로젝트명·사용자명·파일명 같은 식별자를 번역하는 것은 실사용 위험이므로
원문 준수는 별도 실패로 기록한다.

Pi 압축은 keepRecentTokens128에서 큰 로그가 포함된 최근 user turn을 보호했다.
실제 압축 후 요청에도 해당 로그가 남아 있었다. 압축 기능 부재를 뜻하지 않는다.
공식 지원되는 보존 설정32의 추가 시험에서는 원문7/7을 답했지만 입력6102→6311로 여전히 늘었다. 원래 시험과 분리하며, 이 한 번의 원문 회복이 설정32 때문이라고 단정하지 않는다. 공식 prepareCompaction을 원래 native 세션에 적용해 보니0/1은 마지막 assistant,16은 마지막 user,32/64/128은 큰 로그 user부터 보존했다. 설정16의 실제 추론은243.01초에 원문7/7로 통과했고 입력6103→2628로 약56.9% 감소했다. 같은 모델의 압축 기능이 실제 동작함을 확인했다. 16은 경계 검증용 값이며 운영 기본값으로 적용하지 않았다. 요약 손실과 과도한 원문 보존 사이의 균형은 운영 문맥 크기에 맞춰 검증해야 한다.
Hermes는 요약·보호 문구가 길어 입력 감소 폭이 작았다. OpenCode는 이번 표본에서
실제 입력 감소와 원문 보존을 함께 충족했다. transcript 문자 수나 DB 메시지 수로
압축률을 판정하지 않았다.

### 저장소 조사의 한계

출력 파일 structure.json이 세 엔진 모두 없었다. Hermes는 여러 소스를 조사하다
600초에 끝났고, Pi는 `find | sed -n`으로20줄씩 파일 목록을 반복 열람했다.
OpenCode는 소스 읽기를 진행했으나 시험 어댑터의 HTTP timeout360초가 먼저 걸렸다.
600초 외부 제한보다 길게 고친 재시험도600.03초에 결과물 없이 종료됐다. 원래360초 제한 사례와 구분한다. 재시험 native-progress.json에는 완료된 도구 호출이 보존돼 있어, 자동 result의 tool_calls0을 실제 미실행으로 해석하면 안 된다. 이 준비 문제를 모델 품질 실패로
합산하지 않는다. 장시간 조사에서는 모델·도구 선택·CPU 오프로딩 지연·제한 시간이
함께 영향을 주므로 '저장소 이해가 불가능하다'는 결론도 내리지 않는다.

## 엔진 선정·제품 적용

**기본 대체 엔진으로 Pi1.3.0을 우선 선정한다.** 이 표본에서 기본 편집/셸/실행
품질이 충분했고, baseline system+도구 입력이 약1.9K로 Hermes약4.7K 및
OpenCode약5.4K보다 작았다. 단순 과제의 경과 시간도 짧은 편이었다. 공식 SDK의
세션 파일 재개와 native 압축·편집을 사용할 수 있다. 추가 압축 시험에서 실제
입력 감소와 원문7/7을 함께 확인했다. 이 선택은 단일 표본과 해당 설정에 근거한
환경별 결정이며 모델·엔진의 보편 순위를 뜻하지 않는다.

OpenCode1.19.3도 유효한 대안이다. 첫 압축 시험부터 원문7/7·실제40.5% 감소를
충족했고 HTTP/SSE/승인 API가 JVM 연결에 적합하다. 다만 기본 입력 부담이 더
크고 별도 서버 운영이 필요하다. Hermes는 실제 수정·계획·기억은 가능했으나
최소64K 요구와 긴 요약, 애매한 삭제의 선실행이 이번24GB 환경에 불리했다.

제품 적용 시 경계:

1. Pi가 모델 반복 실행, native 도구 구현, canonical session과 compaction을 담당한다.
   기존 커스텀 계획/진척 강제·문맥 요약 루프를 경쟁 엔진이나 fallback으로 남기지 않는다.
2. ServerManager는 Discord 사용자/채널/프로젝트 연결, 소유자·역할·설정 revision
   검사, 독립 위험 검토와 명시적 승인·중단, 동의한 추론 실행기 연결을 담당한다.
3. Pi의 cwd는 보안 sandbox가 아니다. 이번 임시 OS sandbox 통과를 운영 권한 검증으로
   확대 해석하지 않는다. 기본 도구 실행 직전 backend 승인에 연결하고 거부/만료/
   설정 변경/채널 소유자 불일치 시 실제 도구가 실행되지 않는 기능 검증이 필요하다.
4. 제품의 Thinking/실행창/사용자 압축 한도 설정을 존중한다. 이번 thinking없음,
   64K profile이나 진단용 keepRecent16을 운영 기본으로 그대로 이식하지 않는다.
5. Discord 일반 답변/Thinking/툴 턴·실시간 출력·사용량·stop/steer/reset과 첨부
   파일 연결을 검증한다. Node 및 pinned Pi runtime의 설치·상태·업데이트도 관리한다.

**이번 브랜치는 벤치마크와 선정까지만 완료했다. 운영 엔진 교체·설치판·릴리즈는
아직 적용하지 않았다.** 전체 회귀·다른 OS·운영 Discord 연결 시험은 미실행이다.
Strata ready-file 수정은 별도 fix/strata-ready-lifecycle 브랜치이며 아직 이번
벤치마크 브랜치에서 릴리즈하지 않았다.

## 정리와 보존

- 모든 시험 모델 해제를 확인하고 전용 localhost11435 Ollama를 종료했다.
- 기존 localhost11434 Ollama0.40.4는 응답하며 게임/운영 앱은 재시작하지 않았다.
- 정리 시 memory pressure 원시 상태1. wired_limit_mb20480 유지. 스왑이 즉시0으로
  돌아온다고 주장하지 않는다. 실제 기록은 cleanup-before/after-stop.json에 있다.
