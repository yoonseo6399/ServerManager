31B 실제 오류: `model requires 18.0 GiB but only 15.5 GiB are available (after 512.0 MiB overhead)`. 다운로드는 완료했으나 현재 Ollama 한도에서 추론 전에 거부되었다. 메모리 한도/양자화를 임의로 바꾸지 않았다. 다른 실행기에서 선택할 수 있도록 모델 선택지는 제공한다.

파일 과제는 원래 `alpha\nkeep=42\nomega\n`를 보존하고 keep=42 다음·omega 앞에 문구를 넣는다. 성공한3모델의 실제 전체 파일 바이트는 `alpha\nkeep=42\nBENCH_ADDED_7D31\nomega\n`와 일치하며 read_file→write_file→read_file을 실행했다. 완료 답변만으로 합격 처리하지 않았다. 명시적 승인 정책에서 해당 임시 파일의 저장 승인만 시험 콜백이 제공했다. 운영 파일/Discord 전송은 없다.

Python은 모델이 작성한 코드를 그대로 실행해 다음5줄을 비교했다. 불필요한 import/파일/네트워크 기능은 AST에서 차단하고 실행3초 제한을 적용했다. 뒤쪽 공백/끝 줄바꿈 개수만 정규화하며 앞쪽 공백과 별 개수는 엄격히 비교했다.

```text
    *
   ***
  *****
 *******
*********
```

최초 시험은 일반30B/Gemma12B가 마지막LF 누락, Coder가 표시 줄 번호까지 저장하는 실패를 보였다. Coder의 최초 Python에는 잘못된 `}{`가 붙어 구문 오류였다. 읽기 도구의 끝 줄바꿈 정보 누락을 보완하고 줄 번호는 메타데이터라고 명시한 뒤 같은 과제를 다시 시험했다. 최초 실패도 JSON에 보존했다. 시험 자체의 /var vs /private/var 경로 비교를 수정했고 캐시로 생략된 Gemma2회는 제외한 뒤 실제 실행했다.

모델별 과제당1회다. 지원 모델 Thinking=true/Coder=false, 실행 창8192·출력4096, 모델 원래 샘플링 기본값을 사용했다. 파일 시간은 적재부터 위험검토·문맥압축·저장·재조회·최종 보고를 포함한다. Python 시간은 그 뒤 같은 모델의 새 대화에서 코드 생성+실행이다. Qwen은 GGUF Q4_K_M, Gemma는 Ollama MLX로 백엔드·정밀도가 같지 않다. GPU 값은 파일 과제 중1초 간격 Ollama size_vram 보고값이며 전체 시스템 RAM 사용량이 아니다. 스왑은 기존 사용량과 다른 앱 영향을 받는 시스템 전체 값이므로 모델만의 원인으로 단정하지 않는다.

이번 두 작은 과제에서는 Coder가 빠르고 Gemma12B도 성공했다. 최초 실패와1회 표본을 고려하면 일반 코딩·복잡한 도구 사용·권한 판단의 우열로 일반화할 수 없다. 일반14B·실제Discord·다른OS·전체 테스트는 이번 벤치마크에서 미실행이다.
