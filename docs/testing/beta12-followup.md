# Beta 11 이후 실제 봇 로그·명령 실행 재현

## 확인한 환경과 기록

실행 중인 관리 앱과 추론 실행기는 Beta 11이었다. 관리 Mac에 SSH로 접속해 현재 채널 대화·계획·문맥 프로필·앱 로그를 읽었다. 대화/계획 파일은 2026-10-18 16:11에 마지막으로 저장돼 있었다. 운영 앱·봇·실행기·게임호스트를 재시작하거나 운영 프로젝트를 수정하지 않았다.

운영 원문은 `build/bot-followup-evidence/private/`에 비공개로 보관하며 Git·릴리즈에 포함하지 않는다. 아래는 계정·채널 ID와 운영 경로를 뺀 분석이다.

## 실제 문제를 분리한 결과

| 관측 | 판정 | 이번 조치 |
| --- | --- | --- |
| 짧은 “run_command로 Python을 실행하고 조회하지 말라”는 요청이 서로 겹치는 요구사항 6개로 확대됨 | 파일 이름이 없는 짧은 요청도 보조 추출 모델에 넘긴 구현상 과도한 분해 | 500자 이하 비목록 요청을 원문 한 항목으로 유지. 실제 문구를 회귀에 추가 |
| 모델이 run_command를 사용할 수 없다고 말하고, 읽기 전용 sh로 Python 실행을 요청한 뒤 조회를 반복 | 추가 도구를 select_tools로 등록하는 단계와 모델의 도구 선택 능력 사이 문제. 권한 심사에 도달하기 전 | 새 임시 프로젝트에서 실제 14B로 재현. 규칙·프롬프트·권한을 더 완화하는 수정은 하지 않음 |
| 대화 요약은 merge_files.py의 출력 대상을 수정했다고 주장하지만 이후 원문 조회는 이전 대상 그대로 | 요약의 완료 주장을 실행 증거로 신뢰할 수 없음. 원래 요청의 모든 앞뒤가 압축돼 있어 당시 의미적 성공을 확정할 수도 없음 | Beta 11의 원문 읽기·현재 파일 지문 검사는 유지. 요약/문맥 설계를 추가로 실험하는 것은 사용자 지시에 따라 중단 |

**모델이 작아서 생긴 문제라고 확정하지 않는다.** Beta 11에서 추가한 2단계 도구 등록 설계도 조사 대상이다. 새 14B 세션에서 재현돼 오래된 대화만의 문제는 아니지만, 더 강한 모델과 직접 등록 방식의 비교 없이는 모델 자체와 하네스 설계를 분리할 수 없다. 파인튜닝이 꼭 필요하다고 결론 낼 근거도 없다. 이 부분은 미해결로 보고하며 프롬프트 덧붙이기나 강제 실행으로 성공처럼 포장하지 않는다.

## 직접 실행한 LLM 시험

임시 폴더에 `a.txt`, `b.txt`, `merge_files.py`를 준비했다. Python 스크립트는 두 원본을 보존하면서 `ab.txt`에 정확히 합치고 `COMMAND_PROBE_6812`를 출력한다. 요청은 run_command로 한 번 실행하고 조회하지 말라는 내용이다. 제품의 실제 공식 도구 등록·엔진·독립 검토·승인 경로를 사용하며 Discord로 메시지를 보내지 않는다.

| 모델 / 창 | 실제 결과 | 관측 |
| --- | --- | --- |
| Qwen3 30B / 8K | 로딩 중 시험 중단, 답변 없음 | 15.0초에 압력 임계 4. 요청 프레임 1개, 완료 응답 없음. 시스템 스왑 최대 증가 약 3249 MiB. 모델 해제 뒤 별도 확인에서 압력 정상 1 복귀. Metal 설정 변경 없음 |
| Qwen3 14B / 8K | **실패 재현** | JUnit 98.6초(전체 시험 103.4초). select_tools 미사용, sh로 Python 실행 요청 → 검증 거부 → 중단. 실제 실행 도구 0개, ab.txt 생성 안 됨. a/b 원본은 보존. 압력 정상 1, 관측 스왑 증가 0 MiB, 시험 후 모델 해제 |

30B 로딩 실패는 현재 시점의 자원 한계 관측이며 항상 실행 불가능하다는 뜻은 아니다. 이전 30B 16K 실측과도 구분한다. 14B 실패는 정상 압력에서 일어났으므로 메모리가 도구 선택 실패의 원인이라고 볼 근거가 없다. 두 시험 모두 사용자 파일을 수정하지 않았다.

원문은 `command-actor-*.jsonl`, `command-wire-*.jsonl`, `memory-native-*.jsonl`, `run-native-*.json`, `live-native-14b-8192.xml`에 보존했다. 30B는 메모리 중단으로 JUnit 완료 결과가 없으며 통과로 계산하지 않는다. 실제 시험 뒤의 짧은 요구사항 보존 변경은 이 과제에서 이미 사용하던 단일 파일 빠른 경로와 동일하여 도구 선택을 변경하지 않는다.

```sh
python3 scripts/test-agent-command-live.py 8192 14b native
# 30B는 현재 메모리 상태를 먼저 확인할 것. 스크립트가 임계 압력에서 중단한다.
```

## 구현한 별도 기능과 검증

- 음악: 사람 없는 동일 음성 채널에서 연속 60초 후 재생·대기열·연결 정리. 다른 봇은 제외. 사람 복귀·채널 변경·연결 끊김에 시간 초기화. 음성 이벤트와 1초 확인을 결합. 늦은 로드 결과가 재생을 되살리지 않는지 모의 플레이어로 시험.
- 모듈: Minecraft 명령·패널·알림·중복 방지 구현을 실제 모듈로 이동. 서버 제어 포트와 기존 역할 제한 유지, REST로 갱신한 역할과 모듈/권한 거부를 실행 직전 재검사.
- 관리 웹: 모듈별 켜기/끄기, 별도 원자 저장·revision·손상 복구·소유자 재인증. 비활성 모듈 진입 차단과 에이전트 작업 취소. 저장 충돌·미저장 이동 보호를 브라우저 mock API로 시험.
- 기능별 회귀와 React 빌드를 수행했다. 마지막 관리자 API·모듈·서버 제어 묶음은 18개 통과. 모듈 UI Playwright 1개 통과. 앞선 관련 기능 묶음은 108개 중 실제 네트워크 opt-in 2개를 건너뛰고 통과했다. 서로 중복되는 묶음이므로 단순 합산하지 않는다.

전체 스위트·다른 OS·실제 Discord 음성/버튼은 미실행이다. 음악 로그의 YouTube 'video unavailable' 오류는 LLM 실패와 별개이며, 영상 제한인지 소스 플러그인 문제인지는 확인하지 않았다. 설계의 구현 범위는 [현재 구조 점검](../architecture/implementation-status.md)을 따른다.
